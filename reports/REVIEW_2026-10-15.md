## Findings to fix

### 1. P1 · Input-only project backups depend on a successful field calculation

**Location:** `apps/web/app/app.vue`, `exportProjectFile()` and the Export button's disabled expression.

The exporter rejects a missing, busy or stale field, and the button is disabled under the same conditions. A worker constructor or runtime failure clears the field. The user can keep editing but cannot export the committed project unless calculation recovers. This also affects valid scenes that exceed the grid limit. Project JSON stores scene/settings/baseline inputs and regenerates fields, so the field dependency does not protect anything in the exported document.

**Reproduction:** make the Worker constructor throw before loading the application. The recovery message appears and Export is disabled. Confirmed in an isolated Chromium test against a copied production build.

**Change:** export the last committed, validated scene independently of worker state. Continue excluding uncommitted drag previews. Validate with `serializeProject()` and surface an actual document-validation error if necessary.

**Acceptance:** export/import round-trips committed edits and baseline inputs with an unavailable worker, after a runtime worker failure, and while recomputation is pending.

### 2. P2 · Accepted home dimensions can produce an unsolvable field

**Location:** `apps/web/app/components/HomeBuilder.vue`, dimension validation; `apps/web/app/app.vue`, `postField()`; `packages/engine.ts`, `computeField()`.

The rectangle form accepts dimensions up to 100 m per side, and calibrated image dimensions can reach 200 m. Every balanced request uses a fixed 0.25 m step, while the engine rejects more than 100,000 cells. An accepted 80 × 80 m home produces 320 × 320 = 102,400 cells. Creation succeeds and autosaves the project, followed by a grid error. Restarting repeats the same error. Export is also blocked by finding 1.

**Reproduction:** create a rectangle with width/depth 80 m. The builder closes successfully; the worker reports the 100,000-cell limit. Confirmed in Chromium.

**Change:** preflight bounding-box sampling before installing a home. Prefer choosing a disclosed, coarser step within the cap, with a common step for A/B comparisons; otherwise reject the dimensions before replacing the workspace. Apply the same policy to traced and imported scenes.

**Acceptance:** test just below/at/above the cap and long, narrow or concave footprints. A successfully created home must have a supported sampling configuration.

### 3. P2 · An imported home with no probes displays the previous home's reading

**Location:** `packages/engine.ts`, probe schema; `apps/web/app/app.vue`, `inspectProbe()` and import/restore handling.

The scene/project schemas accept an empty probe list, but `inspectProbe()` returns early without clearing `exact`. After importing such a document, the inspector continues displaying the prior workspace's numeric value, distance and crossing terms. This is a silent association of a reading with the wrong project.

**Reproduction:** export a valid project, replace `scene.probes` with `[]`, give it a distinct project ID and import it. The import succeeds and the old numeric readout remains. Confirmed in Chromium.

**Change:** clear the exact result when no probe exists and show an explicit empty state with an Add probe action. Alternatively require at least one probe consistently at the project boundary; the editor already prevents removing the last probe.

**Acceptance:** importing/restoring a zero-probe scene never retains a reading from another scene. Invalid or absent source/probe states should have explicit inspector behavior.

### 4. P2 · Source controls can target a different emitter than the solver

**Location:** `apps/web/app/app.vue`, `sources` and `source`; `packages/engine.ts`, `evaluatePointValidated()`.

The UI filters emitters by domain and chooses the first array entry. The solver chooses the active emitter. A valid imported project can contain an inactive emitter before the active one, causing the plan marker, source coordinates and direct-path line to represent the inactive source. Moving it changes the displayed position while leaving the calculation unchanged. The cutaway already filters for active emitters.

**Reproduction:** prepend an inactive acoustic emitter at X=4 to an exported demo. After import, the source field displays 4 rather than the active emitter's 2. Moving it to 5 leaves both the reading and physical query hash unchanged. Confirmed in Chromium.

**Change:** derive the computational source with the same active/domain predicate as the engine. If inactive sources remain selectable, expose their state and separate their controls from the active-source controls.

**Acceptance:** inactive emitters before/after the active one, either domain, and scenes without an active emitter produce consistent plan, cutaway and inspector behavior.

## What is working well

- Pure TypeScript sound/RF kernels make numerical behavior inspectable without a browser or GPU. Distance, crossings, provenance and invalid states have explicit contracts.
- Cancellation, preview versions and request identities receive more attention than is typical in an early prototype. Adaptive drags, exact probe readings and one-command drag history are useful foundations.
- Fixed-scale comparisons and same-coordinate probe deltas preserve meaning across edits. Unit distinctions between dBm power and dB differences are explicit.
- The plan fallback, lazy cutaway and storage/worker recovery paths support a broad range of devices. Local image processing and portable project JSON fit the product's privacy model.
- The architectural paper palette and warm/teal fields give the interface a consistent identity. Preserve that visual direction.
- The new all-readings and named-probe work complements the existing multiple-probe scene model. Its naming, selection, same-coordinate baseline and CSV flows pass the refreshed browser suite.

## Structural and usability changes

The first two recommendations are partially implemented as recorded above. The list preserves their original full scope; plan-rendering extraction and UI label/format consolidation remain open.

1. **Extract workspace responsibilities from `app.vue`.** It currently contains project orchestration, history, selection, worker scheduling, pointer interaction, drawing, dialogs and substantial CSS. Extract project storage, scene history and field-job coordination into focused composables; extract plan drawing/coordinate transforms into a plain rendering module. Consolidate imports, restoration and home switching behind one workspace-install path. Vue explicitly supports composables for organizing large components by concern ([Vue guidance](https://vuejs.org/guide/reusability/composables#extracting-composables-for-code-organization)).
2. **Share display contracts.** Centralize palettes, transfer bounds, mask presentation, frequency formatting and source labels across plan, cutaway and A/B. In the inspected Wi-Fi view, the plan source annotation still read “Speaker.”
3. **Improve reading comfort.** Much of the desktop interface uses 9–11 px text. Increase ordinary control and explanation text, reduce simultaneous secondary details, and verify keyboard focus and reading order with a real screen reader. Automated accessibility checks already provide a useful baseline.
4. **Remember settings per domain.** Switching Sound/Wi-Fi currently reconstructs default settings. Preserve the last settings for each domain, and decide explicitly whether frequency and baseline actions participate in the same history as geometry.
5. **Establish a reproducible checkpoint.** Create the initial Git commit after the current increment settles. Tie benchmark/test evidence to a source/build identity and update generated reproduction instructions that still say `pnpm`. Extend performance evidence from the five-wall fixture to representative traced homes and slower devices.

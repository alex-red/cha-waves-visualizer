# Echo Lab

Open **Echo Lab** in the banner below the workspace header. The virtual lab runs in the ordinary static app. The phone experiment uses the optional [satellite relay](PHONE_SATELLITE.md).

## Virtual room experiment

Send a virtual pulse at each of five known positions, or choose **Run all five positions**. The hidden rectangular fixture generates four first-order round-trip delays per position, with reproducible Gaussian timing noise. The inverse receives only positions and unlabeled arrival times; fixture geometry and wall identities are withheld.

At least three distinct, non-collinear positions are required. The solver assigns each capture's four arrivals one-to-one to four axis-aligned walls, fits all four wall coordinates, and rejects hypotheses that do not enclose the positions. It reports timing residuals and competing fits. Fixture dimensions and first-order paths can be revealed separately. The fixture dimension error is an experiment diagnostic, not an accuracy claim for recorded rooms.

The default five-position example uses a 6.4 × 4.8 m room and 0.08 ms timing noise. Changing the fixture resets the virtual scan. Changing timing noise and capturing again regenerates the complete captured subset with the same seed.

## Phone satellite experiment

ECHO-03 repeated-probe acquisition and its software verification are complete: 338 Vitest checks, 22 relay/helper tests, 14 tooling tests, full typecheck, build, security/offline checks and 14 focused Chromium checks passed, including the three repeated-series browser cases. A later real Android five-probe series exercised complete observed input and telemetry without clipping or PCM zero runs ≥5 ms; acoustic timing and wall identification remain unvalidated. The next physical gate is the [staged single-wall ECHO-04 test](ECHO_SINGLE_WALL.md). See the [experiment plan](ECHO_EXPERIMENT_PLAN.md) and use the [reproducible workflow](ECHO_WORKFLOW.md) to inspect saved observations.

1. Build the app and start the satellite server, following [the setup guide](PHONE_SATELLITE.md). For wireless capture, use HTTPS trusted by the phone. For an Android USB first test, connect and authorize the phone, set up the ADB reverse tunnel on the same port, and open the relay desktop at `http://localhost:<port>`.
2. Open Echo Lab → **Phone satellite**. Choose **Wireless HTTPS** or **Android USB** to match the server and phone route, then choose **Pair a phone**. Check the displayed phone origin. The QR code is generated locally and contains an expiring session secret in the URL fragment.
3. Scan with the phone's normal camera app and open the link in Chrome; the USB option opens `http://localhost:<port>` through the active tunnel. Choose **Pair device**. This only joins the session; recording requires a separate action.
4. Establish a fixed coordinate origin and axes parallel to the room walls. Enter the phone's measured X/Y position in metres. Position is manual; the phone does not estimate it.
5. For repeated measurement at one pose, enter manual height (0–5 m), orientation (`screen-up`, `screen-down`, or `upright`), heading (0–<360 degrees clockwise from +X, manually reported), and speaker volume (0–100%, user reported). For a flat phone, heading is the direction of its top edge; for an upright phone, it is the direction the screen faces. These are not sensor readings. The batch uses software playback gain 0.1; hardware volume is unchanged.
6. Choose **Record five sweeps**. One MediaStream and AudioContext run to a 1 s software-clock warmup target, then record five separate 700 ms mono PCM probe windows scheduled at least 1 s apart. The first probe waits until the target is reached; if the context is delayed, it starts later. An interrupted warmup may produce a shorter partial manifest with no captured probes. Each attempt is recorded as captured, interrupted or not started. Completed probes remain available if a later attempt is interrupted. Hiding/leaving the page, microphone track end or AudioContext stop cancels acquisition; the microphone stops before review or send. The single **Record sweep** compatibility mode remains available. The browser requests disabled echo cancellation, noise suppression and automatic gain; reported settings and continuity describe browser observations and do not prove that hardware processing is absent or measure acoustic arrival time.
7. Review the batch, then send or download its local JSON. Upload is atomic, and retries reuse stable IDs. Each probe consumes one of the 12 relay/scan capture slots; a rejected over-limit upload preserves existing captures. Three poses with five repeats per pose require exporting the current scan and starting a new pairing session between poses. Successful sends appear on the desktop through same-origin polling.
8. Choose **Analyze recorded sweeps**. A worker decodes PCM16 and performs FFT matched correlation against the emitted chirp. For each recording, explicitly identify the direct-sound peak and then select later candidate arrivals. The solver uses delays relative to that chosen direct peak. Select different peaks if the fit is inconsistent.
9. **Export scan JSON** to save a portable copy before closing the lab. Version 3 recorded scans preserve original PCM, measurement positions, capture IDs, stable peak-review selections, acquisition metadata and optional batch manifests. Synthetic scans preserve their fixture and captures. Version 2 imports preserve PCM and reviews with telemetry unknown; version 1 recorded imports reset the old unkeyed review selections and receive no invented batch history. Reconstruction results are derived and recomputed when a scan is imported; pairing tokens and session secrets are never exported. See the [scan format](ECHO_SCAN_FORMAT.md) for the schema and migration behavior.
10. Importing a scan replaces the current Echo Lab experiment. Use **Restore previous scan** to undo that replacement. Echo Lab does not autosave scans, so export any work you want to keep.

## Next physical gate: one known wall

Follow the [single-wall protocol](ECHO_SINGLE_WALL.md), inspecting the first five probes before requesting the next pose. A defensible wall track should shift later by approximately 5.83 ms per metre of perpendicular movement, measured relative to an identified direct feature within each capture. Keep height, orientation, heading, volume, axes, surface and nearby-body placement fixed. The 0.3 ms repeatability gate applies to candidate-minus-direct delay, not software-clock lag. The protocol defines capture counts, new scan/pairing boundaries, fixed detector settings, integrity checks and stopping conditions.

## Compare recordings before choosing walls

Received or imported recordings show a **Does the response move?** comparison. It aligns candidate peaks to the strongest peak in each recording, independently of the manually chosen direct arrival. This comparison never chooses a direct arrival or changes wall selections. It highlights a later candidate only when its delay stays within 0.3 ms across all analyzed recordings and the positions cover both axes: at least three non-collinear poses, 0.5 m spans in X/Y and a triangle area of at least 0.125 m². Similar delays may come from the device, floor or ceiling; they do not establish vertical wall reflections. Missing or moving shared candidates do not by themselves validate a room fit.

Signal integrity checks run in a worker against the original PCM, including when a scan already contains peak reviews. They report near-full-scale samples (absolute amplitude ≥0.999) and exact-zero runs lasting at least 5 ms, with intervals measured from the recording start. Acquisition counters separately distinguish missing input, unobserved windows and zero-valued samples supplied as present input. Legacy recordings have unknown continuity; no samples are filled, shifted or repaired. Checks are recomputed rather than stored in scan JSON.

A wireless Android Chrome test in a large open-plan kitchen collected recordings at `(0,0)`, `(1,0)` and `(0,1)`. The strongest later candidate stayed at approximately +1.98, +1.94 and +2.04 ms despite both orthogonal moves. The recordings did not provide four identifiable wall arrivals per position, so no physical room reconstruction was established. The capture and transport worked; the single-phone acoustic measurement remains experimental. Original recordings and session secrets are not included in this repository.

For a batch, the offline repeatability report counts a probe as eligible only when it has AudioWorklet sample-frame provenance, observed continuity with zero missing and unobserved frames, and a strongest matched-peak reference with a scheduled comparison. It computes spread only with at least two eligible probes, using strongest-reference-minus-schedule offsets. This measures repeatability of the software-clock comparison; it does not identify a wall or establish acoustic arrival timing.

## Physical and operational boundaries

- This is a first-order rectangular-room experiment at an assumed sound speed of 343 m/s. It does not solve arbitrary furnished geometry, room modes, diffraction, late reverberation or source directivity.
- Speaker and microphone are treated as colocated. Their actual separation, phone DSP, latency and distortion introduce errors. Bluetooth audio adds further uncertainty; use the phone's built-in audio for an initial experiment.
- Peak detection is a candidate generator. A direct path can be weak or absent. Floor, ceiling, furniture and higher-order reflections may be stronger than wall returns. A plausible rectangular fit does not validate the interpretation.
- Fit quality describes agreement with selected arrival times. It is not physical confidence or a calibrated uncertainty interval.
- The satellite server accepts at most twelve recordings per session, with a thirty-minute expiry. An over-limit capture or batch is rejected without evicting existing recordings. By default it holds audio only in memory; the optional [owner API](ECHO_LOCAL_API.md) privately archives accepted PCM/batches. Desktop-only reviews still require export. Ending a session leaves received desktop copies available until the lab closes. Closing the lab retires its session.
- Echo Lab is an independent experiment. It does not alter home geometry, the direct-field heatmap or project JSON. Scan JSON is a separate artifact; importing replaces the current experiment and can be reversed with **Restore previous scan**. Scans are not autosaved.
- The ordinary static preview keeps microphone access disabled. Only the optional satellite server permits same-origin microphone access. Plain LAN HTTP cannot provide phone microphone capture.
- Android USB is an optional transport for an initial phone test, not automatic device provisioning. USB debugging must be enabled and authorized manually, and the data cable must remain connected. It does not create a trusted LAN certificate. The helper's `--remove` option removes only the selected port's reverse mapping.
- The USB helper is present, but no attached-device run has been verified. Wireless Android Chrome capture has been exercised in a real room; this did not establish room-mapping accuracy. Browser checks and synthetic room fits do not establish that result either.
- Phone capture uses AudioWorklet when available, with a sample-frame 700 ms analysis window and 100 ms pre-roll. A labeled `ScriptProcessorNode` fallback reports approximate timing and unavailable continuity. Requested settings and browser-reported applied settings are not proof of unprocessed hardware audio. Software checks do not establish physical telemetry quality or room accuracy.

## Verification

ECHO-03 software verification passed 338 Vitest checks, 22 relay/helper tests, 14 tooling tests, full typecheck, build, security/offline checks and 14 focused Chromium checks, including three repeated-series browser cases. They exercise the worklet with a fake microphone and do not establish Android capture quality, physical telemetry validity, acoustic calibration or room-mapping accuracy. The [workflow guide](ECHO_WORKFLOW.md) documents the offline report and focused test commands.

Earlier baseline verification on October 16, 2026: 285 unit tests, seventeen relay/Android-helper tests, full typechecks, static generation, fixture checks, security-header checks and offline-artifact verification passed. All 147 Chromium cases passed across the full suite and focused reruns. The six-worker run had thirteen failures and two unrun cases; the affected regression files passed with one worker (29 checks), and the phone test passed after a delayed-response test-fixture race was corrected. Fourteen targeted WebKit checks passed. Chromium used the official Chrome for Testing 156 build with `channel: 'chromium'` because the separate headless-shell download timed out; WebKit was 27.2. Browser binaries were restored in temporary storage because the normal Playwright cache was empty.

Coverage includes USB localhost QR pairing, manual setup guidance, scan import/export and restore, invalid-file preservation, new-recording review stability, accessibility and offline workspace checks. The fake-microphone test verifies both recorder paths, active-background cancellation and track cleanup, cancel-send and upload-timeout retries with identical capture IDs and PCM, and server deduplication after an interrupted acknowledgment. No Android device was attached during the local connection check, so USB hardware behavior and physical room accuracy remain unvalidated.

`bun run test` covers inverse geometry, translated origins, degenerate positions, invalid data, seeded noise, FFT correlation, PCM encoding and microphone cleanup. `bun run test:satellite` covers the relay protocol, session lifecycle, bounds, origin restrictions and injected ADB setup/check/cleanup, including existing-port conflicts and real reverse-list formats. Browser tests cover virtual reconstruction, QR pairing, capture transfer, explicit timing references, polling stability, accessibility and responsive layouts. The Chromium recording test uses a fake microphone; it does not establish physical room-mapping accuracy.


This implementation is a bounded experimental prototype, not a reproduction of either research system.
